# dotclaude

Shared Claude Code configuration repo symlinked into `~/.claude/`. See @README.md for full documentation.

**Scope reminder:** Everything in this repo root is symlinked to `~/.claude/` and operates at **user level** (applies to all projects). The `.claude/` directory inside this repo is **not** symlinked — it is project-level config for this repo only.

**Prerequisites:** Commands and agents assume project-level prerequisites documented in `README.md`. Do not flag these as missing or incorrect.

## Rules for Changes

- **Always update `README.md`** when adding, removing, or changing any rule, command, skill, agent, hook, output style, template, or other configuration. Keep the README in sync with the actual repo contents.
- **Don't document project-level `.claude/` files in `README.md`** — the README catalogs only the user-level artifacts symlinked from the repo root. Files under this repo's own `.claude/` directory (e.g. `.claude/commands/`, `.claude/settings.json`) are project-level config for this repo only and must not be added to the README tables.
- **Keep README entries short** — describe what an artifact is for in a phrase, not how it works. Its own file is the single source of its steps, inputs, and edge cases; repeating them in the README doubles the maintenance and rots.
- **Keep the README's `settings.json` summary to principles only** — describe the security posture and intent, never individual entries (permission patterns, excluded commands, domains, env vars). `settings.json` is the single source of those details; listing them in the README rots. Adding or changing a settings entry needs no README change unless it changes a principle.
- **Keep it general** — this repo is config for anyone, on any project and any machine, so its content makes sense to a stranger who clones it. Names, terms, paths and examples stay generic rather than drawn from a particular project, organization or person. Use portable forms — `~`, `$HOME`, or wildcards (e.g. `bash */.claude/skills/*.sh *`, not `bash /Users/alice/.claude/skills/*.sh *`).
- **Every command file** (`commands/*.md`) must include `disable-model-invocation: true` in its YAML frontmatter.
- **Acknowledge sources** — when any content is added or inspired by a plugin found via the `plugin-browser` skill (whether a new skill/command/agent or content incorporated into existing files like rules), add the reference repo to the `Acknowledgments` section in `README.md`.
- **Run `make install` after adding or removing a top-level entry** in a linked directory (a new skill, command folder, hook script, …) — nothing links it otherwise.
- **Hook scripts go in `hooks/`** — shell scripts registered as hooks in `settings.json` belong in `hooks/`. Helper scripts that commands, skills, or settings invoke at runtime belong in `scripts/`.
- **No cross-references irrelevant to the usage context** — name another artifact, or the mechanism behind a rule, only when the reader acts on it: reads it, applies its vocabulary, invokes it, sets the flag, or reacts to the value. A source the reader genuinely draws on earns its place (e.g. linking the skill whose vocabulary they must use). Everything else is noise the reader never acts on — how some *other* artifact consumes this one, which command produced a file they only need to edit, *why* a section is absent when "absent → treat as not run" is all they need, or that a hook enforces a rule as a "backstop" when the rule itself is the whole instruction. The reader obeys the rule, not the mechanism enforcing it. The test is relevance to the usage context, not whether a cross-reference exists.

## Engineering Philosophy

The engineering skills (`tdd`, `improve-codebase-architecture`, `grill-me`) are the source of truth for how this repo thinks about building software. The `design-change`, `write-plan` and `execute-plan` skills are a downstream pipeline built directly on top of them: design checked against the code → research and deep-module design with a self-review → test-first execution. The whole engineering domain rests on seven tenets:

- **Deep modules.** Prefer modules whose interface is small relative to the functionality they hide (high *leverage*), so complexity is concentrated in one place (*locality*). Reason about architecture with the exact vocabulary in [`improve-codebase-architecture`](../skills/improve-codebase-architecture/SKILL.md): *module, interface, implementation, depth, seam, adapter, leverage, locality* — not "component," "service," or "boundary." Apply the **deletion test** to judge whether a module earns its keep.
- **Behavior-first testing.** Tests verify behavior through public interfaces, never implementation details — *the interface is the test surface*, so a good test survives any internal refactor. Build in **vertical slices** via the `tdd` red-green-refactor loop (one test → one implementation → repeat), never all-tests-then-all-code.
- **Domain-grounded.** Use the project's canonical vocabulary from `GLOSSARY.md` (or the per-context files a root `GLOSSARY-MAP.md` points to) and respect the decisions recorded in `docs/adr/`. Sharpen fuzzy terms into the glossary as they crystallize; don't silently re-litigate an ADR.
- **Evidence over speculation.** Explore the codebase and research docs before designing; ground every plan in real prior-art patterns and tests rather than inventing new ones.
- **Goal-anchored.** Every step serves the user's real goal, not only the literal request. Find the intent behind the ask before deciding how; when request and goal diverge, say so rather than build what was literally asked. Write the goal down once and have each later stage re-read it, and make "does this still reach the goal?" the first question of every check.
- **Validate continuously.** No stage hands off unchecked work. Each one checks its output against the code, the goal and the deep-module design before the next stage starts — design critique and an independent fact-check, the plan's self-review, an architecture review of what a design or plan touches, and the tests.
- **Human-first.** Optimize for the person, not the artifact. Every interactive step gauges what the user already understands from their messages, starts simple, defines terms, and raises its level as they show understanding — and never asks a question they can't answer at their current level.

**When editing or adding any rule, skill, or command in this engineering domain, stay consistent with these tenets and with the existing artifacts** — reuse the established vocabulary exactly, keep tests behavior-focused, preserve the deep-module framing, and keep the planning pipeline aligned with the skills it builds on. A change to one engineering artifact must not drift from the language or principles of the others.
